# 网页端控制硬件执行器功能说明

## 更新日期：2026-07-31

---

## 功能概述

实现了网页端远程控制硬件执行器的完整功能。用户可以在网页上通过各种控制卡片（开关、滑块、角度选择等）控制硬件执行器，控制指令通过服务器实时推送给硬件端，硬件执行后发送回执确认，服务器收到回执后更新页面状态，确保控制闭环。

### 核心特性

- **多种控制类型**：支持布尔值、整数、角度、浮点、字符串五种控制类型
- **RGB-LED专项控制**：支持预设颜色、自定义RGB、白色亮度、颜色名称等6种控制方式
- **摄像头专项控制**：支持视频流嵌入、云台控制、颜色追踪、5种颜色预设、重置等控制方式
- **实时通信**：WebSocket实时推送控制指令，减少轮询开销
- **回执确认机制**：发送指令后等待硬件回执，收到回执才更新页面
- **乐观更新**：命令执行成功后立即更新前端UI，无需等待服务器数据同步
- **双通道回执**：WebSocket + HTTP双通道同时发送回执，支持幂等处理
- **超时提醒**：30秒未收到回执自动标记超时并提醒用户
- **区域自动划分**：基于IP地址自动划分设备区域，同一IP设备归为同一区域
- **控制卡片自适应**：根据硬件上报的控制类型自动加载对应控制UI
- **指令锁定机制**：指令执行期间锁定执行器，防止重复发送
- **命令ID跟踪**：轮询检查命令状态时验证命令ID，避免多命令状态混淆
- **Feedback保留机制**：设备未上报feedback时保留原值，避免被意外覆盖

## 架构设计

### 数据流程

```
网页端 → 服务器（WebSocket/HTTP） → 硬件端 → 执行设备
  ↓           ↓                        ↓          ↓
发送指令   存储指令（pending）       接收指令    执行指令
  ↓           ↓                        ↓          ↓
乐观更新   推送指令到硬件            执行回执    反馈状态
  ↓           ↓                        ↓          ↓
立即显示   更新数据库（executed）   发送回执    完成执行
  ↓           ↓                        ↓          ↓
异步同步   双通道回执处理            状态同步    -
```

### 性能优化指标

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 命令创建耗时 | ~100ms | ~50ms | 2倍 |
| 状态轮询耗时 | ~1400ms | ~60ms | 23倍 |
| 前端显示延迟 | ~2000ms | ~300ms | 6.7倍 |
| 数据库操作数 | 3次/请求 | 1次/请求 | 3倍 |

### 技术方案

采用 **WebSocket实时推送 + HTTP轮询备份** 的双模式方案：

1. **WebSocket模式（推荐）**：
   - 硬件端与服务器建立WebSocket长连接
   - 服务器实时推送控制指令到硬件端
   - 硬件端通过WebSocket发送回执确认
   - 实时性高，延迟低（<100ms）

2. **HTTP轮询模式（备份）**：
   - 硬件端定期查询服务器获取待执行指令
   - 硬件端执行指令后通过HTTP上报回执
   - 适用于不支持WebSocket的设备

## 执行器控制类型

### 五种控制类型

| 控制类型 | 说明 | 交互控件 | 适用设备示例 |
|---------|------|---------|------------|
| boolean | 布尔值控制（on/off） | 开关按钮 | 水泵、LED灯、电磁阀、继电器 |
| integer | 整数值控制（0-100） | 滑块 + 数值输入 | 电机速度、风扇档位、亮度调节 |
| angle | 角度控制（0-180/360） | 角度滑块 + 刻度 | 舵机、阀门开度、遮阳板角度 |
| float | 浮点值控制 | 精细滑块 + 小数输入 | 精确参数调节 |
| string | 字符串指令 | 下拉选择 / 文本输入 | 自定义指令、模式切换 |

### 控制类型配置

硬件端在上报数据时通过 `control_type` 和 `control_range` 字段指定控制类型：

```json
{
  "node_id": "motor_001",
  "type": "motor",
  "state": "on",
  "control_value": 60,
  "control_type": "integer",
  "control_range": {
    "min": 0,
    "max": 100,
    "step": 5,
    "default": 0
  }
}
```

## 数据库设计

### 执行器表（actuators）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | VARCHAR(50) | 执行器ID（主键），格式：{PREFIX}-{gatewayId}-{nodeId} |
| name | VARCHAR(100) | 执行器名称 |
| type_id | INT | 执行器类型ID |
| type | VARCHAR(50) | 执行器类型标识 |
| location | VARCHAR(200) | 安装位置 |
| area | VARCHAR(100) | 区域名称 |
| status | VARCHAR(20) | 在线状态：online/offline |
| state | VARCHAR(20) | 运行状态：on/off |
| mode | VARCHAR(20) | 控制模式：auto/manual |
| control_value | DECIMAL(10,2) | 当前控制值（电机速度、舵机角度等） |
| control_type | VARCHAR(20) | 控制类型：boolean/integer/angle/float/string |
| control_min | DECIMAL(10,2) | 控制最小值 |
| control_max | DECIMAL(10,2) | 控制最大值 |
| control_step | DECIMAL(10,2) | 控制步进值 |
| control_default | DECIMAL(10,2) | 控制默认值 |
| farm_id | INT | 农场ID |
| last_update | TIMESTAMP | 最后更新时间 |
| locked | TINYINT | 锁定状态（0=未锁定，1=锁定） |
| feedback | JSON | 设备回馈数据（状态、方向、速度、颜色等） |

### feedback字段结构

```json
{
  "state": "on",
  "control_value": 50,
  "color": {"r": 255, "g": 128, "b": 0},
  "brightness": 60,
  "direction": "forward",
  "speed": 0.5,
  "pattern": "alarm"
}
```

**Feedback保留机制说明**：
- 设备上报时如果未包含feedback字段，服务器会保留原值（使用COALESCE函数）
- 避免设备周期性上报时意外覆盖已存储的feedback数据
- 仅当设备主动上报feedback时才会更新

### 控制指令表（actuator_commands）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT | 指令ID（主键，自增） |
| actuator_id | VARCHAR(50) | 执行器ID |
| command | VARCHAR(20) | 控制命令：on/off/value/color/preset |
| control_value | DECIMAL(10,2) | 控制值（command=value时使用） |
| status | VARCHAR(20) | 指令状态：pending/executing/executed/failed/timeout |
| created_at | TIMESTAMP | 创建时间 |
| executed_at | TIMESTAMP | 执行时间 |
| command_data | JSON | 扩展命令数据（RGB控制参数等） |

### command_data字段结构（RGB控制）

```json
{
  "r": 255,
  "g": 128,
  "b": 0,
  "preset": "orange"
}
```

## API接口

### 1. 发送控制指令（网页端）

**接口地址**: `POST /api/actuators/[id]/commands`

**功能说明**: 发送控制指令到指定执行器。支持普通控制和RGB-LED扩展控制。

**请求参数**:

| 参数 | 类型 | 必填 | 说明 |

| control_type | string | 是 | 控制类型：boolean / integer / angle / float / string / rgb |

| value | number | 否 | 控制值（command=value时使用） |
| r | number | 否 | 红色通道（command=color时使用，0-255） |
| g | number | 否 | 绿色通道（command=color时使用，0-255） |
| b | number | 否 | 蓝色通道（command=color时使用，0-255） |
| preset | string | 否 | 预设颜色名称（command=preset时使用） |

{

### 2. 查询控制指令（硬件端/前端轮询）

**接口地址**: `GET /api/actuators/[id]/commands`

**请求参数**:

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| frontend | boolean | 否 | 前端查询模式（不传则为硬件端模式） |

**前端查询模式** (`?frontend=true`):
- 不执行超时清理（快速响应）
- 只返回最新一条指令
- 响应时间：~60ms

**硬件端查询模式**（不传frontend参数）:
- 执行超时清理逻辑
- 返回最近5条指令
- 响应时间：~140ms

**响应示例（前端查询）**:
```json
{
  "success": true,
  "data": {
    "id": 123,
    "actuator_id": "MT-1-1001",
    "command": "value",
    "control_value": 75,
    "status": "executed",
    "created_at": "2026-07-30T10:30:00.000Z",
    "executed_at": "2026-07-30T10:30:05.000Z"
  },
  "message": "OK"
}
```

### 3. 确认指令执行（硬件端HTTP回执）

**接口地址**: `PATCH /api/actuators/[id]/commands`

**功能说明**: 硬件端确认控制指令执行结果（HTTP方式回执）。支持幂等操作，重复回执不会报错。

**幂等处理说明**:
- 如果命令已是目标状态，直接返回成功
- 处理WebSocket和HTTP双通道回执的竞态条件
- 响应时间：~11ms（优化后）

**路径参数**:

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | string | 是 | 执行器ID |

**请求参数**:

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| command_id | number | 是 | 命令ID（从查询指令接口获取） |
| status | string | 是 | 执行状态：executed / failed |
| control_value | number | 数值控制必填 | 实际执行的控制值 |
| state | string | 否 | 执行器状态：on / off |
| color | object | RGB设备必填 | 颜色信息 {r, g, b} |
| brightness | number | RGB设备可选 | 亮度值 0-100 |

**请求示例（普通执行器）**:
```json
{
  "command_id": 123,
  "status": "executed",
  "control_value": 75,
  "state": "on"
}
```

**请求示例（RGB-LED）**:
```json
{
  "command_id": 124,
  "status": "executed",
  "state": "on",
  "color": {"r": 255, "g": 128, "b": 0},
  "brightness": 60
}
```

**响应示例**:
```json
{
  "success": true,
  "message": "OK",
  "command_id": 123,
  "actuator_id": "MT-1-1001",
  "status": "executed",
  "timestamp": "2026-07-30T10:30:05.000Z"
}
```

## 回执确认与超时机制

### 回执确认流程

```
用户点击控制按钮
      ↓
前端发送控制请求到服务器
      ↓
服务器创建指令（状态：pending）+ 返回命令ID
      ↓
【前端保存命令ID】用于后续状态检查
      ↓
服务器通过WebSocket推送指令到硬件端
      ↓
前端显示"指令发送中..."状态 + 轮询检查
      ↓
硬件端接收并执行指令
      ↓
硬件端双通道发送回执（WebSocket + HTTP）
      ↓
服务器更新指令状态（executed）
      ↓
服务器更新执行器状态和feedback数据
      ↓
【命令ID匹配检查】前端轮询检测到对应命令的executed状态
      ↓
【乐观更新】立即更新本地UI状态
      ↓
异步同步服务器数据（fetchActuators）
```

### 命令ID跟踪机制

为避免多命令并发时状态混淆，前端实现命令ID跟踪：

1. **发送命令时保存命令ID**：
   - 服务器返回命令ID后，前端保存到 `pendingCommandIds` 状态
   - 格式：`{[actuatorId]: commandId}`

2. **轮询检查时验证命令ID**：
   - 前端轮询获取最新命令
   - 检查命令ID是否与保存的ID匹配
   - 如果不匹配，跳过该状态更新（可能是其他命令的回执）

3. **状态完成后清理命令ID**：
   - 命令执行成功/失败/超时后，清除对应的pendingCommandId
   - 避免内存泄漏和状态混淆

### 双通道回执机制

| 通道 | 延迟 | 说明 |
|------|------|------|
| WebSocket | <50ms | 优先使用，实时性高 |
| HTTP PATCH | <15ms | 备份通道，支持幂等处理 |

**竞态处理**：
- 两个通道都可能先到达
- 幂等处理确保重复回执不会报错
- 响应时间：~11ms

### 超时机制

- **超时时间**：30秒
- **超时触发**：发送指令后30秒未收到回执
- **超时处理**：
  1. 指令状态标记为 `timeout`
  2. 执行器自动解锁（locked=0）
  3. 前端显示超时提醒
  4. 允许用户重新发送指令

### 指令状态说明

| 状态 | 说明 |
|------|------|
| pending | 待执行（已创建，等待推送/执行） |
| executing | 执行中（已推送到硬件，等待回执） |
| executed | 已执行（收到硬件回执确认） |
| failed | 执行失败（硬件返回失败） |
| timeout | 超时（30秒未收到回执） |

## 控制卡片自动加载

### 加载逻辑

前端根据执行器的 `control_type` 字段自动加载对应的控制卡片：

1. **优先使用硬件上报的配置**：如果数据库中 `control_type` 有值，使用该配置
2. **使用设备类型字典配置**：如果没有硬件上报的配置，使用设备类型默认配置
3. **默认布尔值控制**：如果都没有配置，默认使用布尔值开关控制

### 控制卡片类型

#### 1. 布尔值控制卡片（boolean）

- **控件**：开关按钮
- **功能**：点击切换 on/off 状态
- **适用**：水泵、LED灯、电磁阀、继电器等

#### 2. 整数控制卡片（integer）

- **控件**：滑块 + 数值输入框
- **范围**：由 `control_min` 和 `control_max` 决定
- **步进**：由 `control_step` 决定
- **适用**：电机速度、风扇档位、亮度调节等

#### 3. 角度控制卡片（angle）

- **控件**：角度滑块 + 角度刻度显示
- **范围**：通常 0-180° 或 0-360°
- **步进**：通常 1°
- **适用**：舵机角度、阀门开度、遮阳板角度等

#### 4. 浮点控制卡片（float）

- **控件**：精细滑块 + 小数输入框
- **精度**：支持小数控制
- **适用**：精确参数调节等

#### 5. 字符串控制卡片（string）

- **控件**：下拉选择框 或 文本输入框
- **适用**：自定义指令、模式切换等

#### 6. RGB-LED控制卡片（rgb / 特殊识别）

- **触发条件**：
  - `control_type === 'rgb'`
  - `type === 'light'` 且 feedback 包含 R/G/B 字段
  - `type === 'light'` 且 name 包含 "RGB"（不区分大小写）
- **控件**：多模式控制界面
- **控制方式**：
  1. **预设颜色选择器**：9种预设颜色快速选择（value 1-9）
  2. **白色亮度滑块**：0-100%亮度调节
  3. **自定义RGB滑块**：三通道独立控制（0-255）
  4. **颜色名称快捷按钮**：直接发送预设颜色名指令
- **实时预览**：显示当前选择的HEX颜色值
- **状态显示**：显示当前状态、亮度、RGB值

**RGB控制命令格式**（已包含control_type字段，直接发送）:
```json
// 预设颜色
{"control_type": "rgb", "command": "value", "value": 1}

// 白色亮度
{"control_type": "rgb", "command": "value", "value": 50}

// 自定义RGB
{"control_type": "rgb", "command": "color", "r": 255, "g": 128, "b": 0}

// 颜色名称
{"control_type": "rgb", "command": "preset", "preset": "orange"}

// 关闭
{"control_type": "rgb", "command": "value", "value": 0}
```

**RGB-LED识别逻辑**（多种方式确保正确识别）:
```typescript
// 方式1：类型直接是 rgb_led
const isRgbLed = actuator.type === 'rgb_led'

// 方式2：类型是 light 且 feedback 包含 RGB 字段
const hasRgbFeedback = actuator.feedback && 
  (actuator.feedback.color || 
   ('R' in actuator.feedback && 'G' in actuator.feedback && 'B' in actuator.feedback))

// 方式3：类型是 light 且 name 包含 RGB（不区分大小写）
const hasRgbInName = actuator.name.toLowerCase().includes('rgb')

// 综合判断
const isRgbLed = actuator.type === 'rgb_led' || 
  (actuator.type === 'light' && (hasRgbFeedback || hasRgbInName))
```

#### 7. 摄像头控制卡片（camera / 特殊识别）

- **触发条件**：
  - `type === 'camera'`
  - `control_type === 'string'` 且 node_id 以 `CAM-` 前缀
- **控件**：视频流 + 多模式控制界面
- **控制方式**：

- **检测帧上传**：硬件端通过 `/api/device/upload-image` 上传带检测框的帧

- 根据控制类型显示对应控制卡片
- 操作后等待回执确认

### 3. 控制操作流程

1. 找到目标执行器的控制卡片
2. 进行控制操作（点击开关、拖动滑块等）
3. 按钮/控件显示"发送中"状态，执行器被锁定
4. 前端每300ms轮询检查命令状态（带命令ID验证）
5. 硬件执行命令并通过双通道发送回执
6. 前端检测到**对应命令的**`executed`状态后**立即乐观更新UI**（无需等待服务器数据同步）
7. 异步调用`fetchActuators()`从服务器同步最新数据
8. 如果30秒内未收到回执，显示超时提醒

### 4. 乐观更新机制

**传统方式**：
```
发送指令 → 等待回执 → fetchActuators → 更新UI
总延迟：~2000ms
```

**乐观更新**：
```
发送指令 → 轮询检测到executed → 立即更新本地UI → 异步同步
总延迟：~300ms
```

**实现方式**：
- 轮询检测到`executed`状态后，直接使用命令数据更新本地state/control_value
- 不等待`fetchActuators()`完成
- `fetchActuators()`作为数据同步兜底，确保最终一致性
- **命令ID验证**：确保只更新当前等待的命令状态，避免状态混淆

### 5. sendControlCommand命令格式处理

前端 `sendControlCommand` 函数支持三种命令格式，自动识别并转换为正确的API请求体：

```typescript
// 判断命令格式的三个条件：
const isAlreadyFormatted = typeof command === 'object' && command !== null && 'control_type' in command
const isRgbCommand = typeof command === 'object' && command !== null && 'command' in command && !('control_type' in command)

// 处理逻辑：
if (isAlreadyFormatted) {
  // 1. 已格式化的API请求体（RGBControlCard直接构造的完整格式）
  //    例如：{ control_type: 'rgb', command: 'value', value: 1 }
  body = command  // 直接使用，不再转换
} else if (isRgbCommand) {
  // 2. RGBCommand格式（包含command字段但没有control_type）
  //    例如：{ command: 'value', value: 1 }
  body = {
    control_type: 'rgb',
    command: command.command,
    value: command.value,  // 或 r/g/b/preset
    // ... 添加其他参数
  }
} else {
  // 3. 标准命令格式（字符串 'on' | 'off' | 'value'）
  //    例如：'on' 或 'value'
  body = {
    control_type: controlType,  // 从设备类型配置获取
    command: strCommand,
    value: value,  // 数值控制时添加
  }
}
```

**RGB控制卡片发送命令格式**（推荐方式）：
- RGBControlCard 组件直接构造包含 `control_type` 的完整请求体
- 避免了中间格式转换可能导致的错误
- 支持所有RGB控制方式（预设颜色、自定义RGB、颜色名称、白色亮度、开关）

```typescript
// RGBControlCard 中的发送函数
const sendRgbCommand = (apiBody: any) => {
  // apiBody 已经是完整格式，直接传递
  onControl(apiBody)
}

// 示例：发送预设颜色

// 示例：发送自定义RGB

```

void WebSocket_OnMessage(const char* message) {
    cJSON* root = cJSON_Parse(message);
    cJSON* type = cJSON_GetObjectItem(root, "type");
    
    if (strcmp(type->valuestring, "command") == 0) {
        cJSON* data = cJSON_GetObjectItem(root, "data");
        int command_id = cJSON_GetObjectItem(data, "command_id")->valueint;
        const char* actuator_id = cJSON_GetObjectItem(data, "actuator_id")->valuestring;

## 状态同步机制

### 核心原则

1. **服务器状态优先**：服务器状态是唯一权威状态
2. **硬件状态仅监控**：硬件上传的状态用于服务器监控
3. **强制同步**：当硬件状态与服务器不一致时，硬件必须强制同步
4. **回执确认**：控制指令必须收到回执才更新页面

### 状态同步时机

1. **硬件端定期上报**：每5-10秒上报一次状态
2. **指令执行后**：执行完指令后立即上报新状态
3. **强制同步后**：收到强制同步指令后立即执行并确认
4. **状态变化时**：检测到硬件状态变化时立即上报

## 故障排查

### 问题1：网页端发送指令失败

**检查清单**：
- 服务器是否正常运行
- 执行器ID是否正确
- 网络连接是否正常
- 浏览器控制台是否有错误信息
- 检查发送的JSON格式是否正确（RGB命令必须包含 `control_type: "rgb"`）

### 问题2：RGB灯控制卡片不显示

**检查清单**：
- 执行器的type字段是否为 `light`
- 执行器的name是否包含"RGB"（不区分大小写）
- 执行器的feedback字段是否包含RGB数据
- 刷新页面后是否正常

### 问题3：控制指令立即显示失败

**检查清单**：
- 命令ID是否正确保存和验证
- 是否有其他命令先到达导致状态混淆
- 检查 `pendingCommandIds` 状态是否正确设置
- 检查控制台日志中的 `[sendControlCommand]` 输出，确认命令格式正确

### 问题4：控制页面更新不及时

**检查清单**：
- WebSocket连接是否正常（查看页面右上角连接状态）
- 硬件端是否通过双通道（WebSocket + HTTP）发送回执
- 前端轮询间隔是否正常（300ms）
- 检查是否收到 `command_status` 类型的WebSocket消息
- 如果WebSocket断开，检查HTTP转发接口（8081端口）是否正常运行
- 硬件端是否能正确处理命令并及时返回回执

### 问题5：硬件端收不到指令（WebSocket模式）

**检查清单**：
- WebSocket连接是否正常建立
- 网关是否正确注册
- 服务器是否正确关联了网关IP和执行器
- 查看服务器日志是否有错误

### 问题7：硬件端收不到指令（HTTP轮询模式）

**检查清单**：
- 硬件端网络连接是否正常
- 执行器ID是否匹配
- 数据库中是否有pending状态的指令
- 查询参数是否正确（gateway_ip）

### 问题8：指令执行后状态未更新

**检查清单**：
- 硬件端是否正确发送回执
- 回执中的command_id和actuator_id是否正确
- 数据库更新是否成功
- 前端WebSocket连接是否正常
- 查看浏览器控制台和服务器日志

### 问题9：Feedback数据被重置

**检查清单**：
- 设备上报时是否包含feedback字段
- 服务器是否使用COALESCE保留原值
- 检查数据库中的feedback字段是否为null

### 问题10：控制卡片显示不正确

**检查清单**：
- 执行器的control_type字段是否正确设置
- 硬件上报时是否包含control_type和control_range
- 设备类型字典中是否有对应配置
- 刷新页面后是否正常

### 问题11：摄像头视频流不显示

**检查清单**：
- 树莓派是否启动了视频流服务（默认8081端口）
- 浏览器是否能直接访问 `http://树莓派IP:8081/stream`
- 设备 feedback 中的 `stream_url` 和 `snapshot_url` 字段是否正确
- 浏览器是否有混合内容拦截（HTTPS页面加载HTTP资源）
- 树莓派和浏览器是否在同一局域网
- 检查防火墙是否放行8081端口

### 问题12：摄像头云台控制无效

**检查清单**：
- 发送的命令是否包含 `control_type: "string"`
- value 字符串格式是否正确（`pan=90,tilt=45` 或 `pan_delta=-10,tilt_delta=5`）
- 角度值是否在 0-180 范围内
- 舵机是否正确连接到树莓派 GPIO
- 查看树莓派日志，是否收到并执行了命令
- feedback 中的 pan_angle/tilt_angle 是否更新

### 问题13：颜色追踪不工作

**检查清单**：
- 是否已开启追踪（`command: "track", value: "on"`）
- 是否选择了颜色预设（`command: "color", value: "red"`）
- HSV 阈值配置是否正确（settings.yaml 的 camera.tracking.color_presets）
- 摄像头视野中是否有目标颜色的物体
- feedback 中的 `found` 字段是否为 true
- target_x/target_y/target_area 是否有合理的值

## 控制更新及时性说明

### 更新延迟分析

控制指令从发送到前端UI更新的延迟主要由以下几个阶段组成：

| 阶段 | 延迟 | 说明 |
|------|------|------|
| 命令创建 | ~50ms | 服务器创建指令并存储到数据库 |
| 命令推送 | <50ms | WebSocket实时推送到硬件端（如果连接在线） |
| 硬件执行 | 视硬件而定 | 通常<100ms |
| 硬件回执 | <50ms | 硬件通过WebSocket或HTTP发送回执 |
| 服务器处理回执 | ~11ms | 服务器更新数据库状态，更新执行器feedback |
| 前端轮询检测 | ~60ms | 前端通过 `?frontend=true` 快速查询模式获取最新状态 |
| **乐观更新显示** | **~300ms** | 用户感知到的总延迟 |

### 延迟优化策略

1. **分离查询模式**：前端查询使用 `?frontend=true` 参数，跳过超时清理逻辑，响应时间从 ~140ms 降至 ~60ms
2. **乐观更新机制**：检测到命令状态为 `executed` 时立即更新本地UI，无需等待 `fetchActuators()` 完成
3. **300ms轮询间隔**：优化前端轮询间隔，在保证性能的同时快速响应状态变化
4. **命令ID跟踪**：精确验证命令ID，避免状态混淆，确保每次更新都是针对当前命令的
5. **双通道回执**：WebSocket + HTTP双通道同时发送回执，确保至少一个通道能及时到达

### 影响及时性的因素

- **WebSocket连接状态**：如果WebSocket断开，命令推送将使用HTTP转发，延迟会增加
- **硬件处理速度**：硬件端的执行速度直接影响回执时间
- **网络延迟**：服务器与硬件之间的网络延迟
- **数据库性能**：MySQL的查询和更新性能

## 注意事项

1. **回执必须发送**：硬件端执行完指令后必须发送回执，否则前端会显示超时
2. **指令ID正确**：回执中的command_id必须与收到的指令ID一致
3. **控制值范围**：控制值必须在control_min和control_max范围内
4. **并发控制**：同一时间同一执行器只能有一个待执行指令（locked机制）
5. **网络稳定性**：确保硬件端和服务器之间的网络连接稳定
6. **WebSocket重连**：硬件端应实现WebSocket断开自动重连机制
7. **超时处理**：30秒未收到回执会自动超时，硬件端应尽快处理并回执
8. **RGB命令格式**：RGB控制命令必须包含 `control_type: "rgb"` 字段
9. **Feedback保留**：设备上报时如果不包含feedback字段，服务器会保留原值
10. **前端刷新**：代码更新后需要硬刷新浏览器（Ctrl+Shift+R）清除缓存的旧JS代码
11. **摄像头命令格式**：摄像头控制命令必须使用 `control_type: "string"`，value为字符串格式（如 `pan=90,tilt=45`）
12. **视频流直连**：摄像头视频流由浏览器直连树莓派8081端口，不经过服务端，需保证浏览器与树莓派在同一局域网
13. **颜色预设范围**：摄像头颜色预设仅支持5种：blue/red/green/yellow/orange，HSV阈值在硬件端 settings.yaml 配置
