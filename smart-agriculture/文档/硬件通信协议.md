# 硬件数据绑定协议说明

## 概述

本文档描述智慧农业平台与硬件设备之间的数据交换协议，包括设备上报协议、执行器控制协议、回执确认协议和WebSocket实时通信协议。

> **更新日期**：2026-08-10
> **完整API参考文档**: 请参考 [API参考文档](./API参考文档.md) 获取所有API接口的详细说明。

### 系统架构

平台采用分布式架构，由三个独立进程协同工作：

| 进程 | 端口 | 职责 |
|------|------|------|
| **Next.js开发服务器** | 3000 | 提供HTTP API、渲染前端页面、数据库操作 |
| **WebSocket服务器** | 8080 | 处理WebSocket实时连接、命令推送、状态同步 |
| **HTTP转发接口** | 8081 | 接收HTTP命令并转发到WebSocket连接（桥梁作用） |

### 命令下发流程

```
用户操作 → POST /api/actuators/{id}/commands → 写入数据库(pending)
    → HTTP POST http://localhost:8081/send-command → WebSocket推送命令
    → 硬件执行 → 双通道回执（WebSocket + HTTP）→ 更新数据库(executed)
    → 前端轮询检测 → 乐观更新UI → 异步同步
```

### 冗余保障

- **优先使用WebSocket**：实时推送命令，响应延迟<500ms
- **降级为HTTP轮询**：WebSocket断开时自动切换，确保命令不丢失
- **双通道回执**：硬件端同时通过WebSocket和HTTP发送回执，支持幂等处理

### 1.3 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| gateway_ip | string | 是 | 网关IP地址，用于区域划分 |
| gateway_type | string | 否 | 网关类型，默认`wifi_sensor` |
| mac | string | 否 | 网关MAC地址 |
| farm_id | number | 是 | 农场ID |
| area | string | 否 | 区域名称，同一IP下的设备默认属于同一区域 |
| nodes | array | 是 | 设备节点数组 |

#### nodes数组元素字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| node_id | string | 是 | 设备节点唯一标识 |
| name | string | 否 | 设备名称 |
| type | string | 是 | 设备类型（temperature/humidity/motor/servo/light/fan/buzzer等） |
| value | number | 传感器必填 | 传感器数值 |
| unit | string | 否 | 单位 |
| location | string | 否 | 安装位置 |
| area | string | 否 | 区域名称（可覆盖网关级区域） |
| state | string | 执行器必填 | 执行器状态（on/off） |
| mode | string | 否 | 执行器模式（auto/manual） |
| control_value | number | 否 | 执行器当前控制值 |
| control_type | string | 否 | 执行器控制类型 |
| control_range | object | 否 | 执行器控制参数范围 |
| **feedback** | **object** | **否** | **设备特有回馈数据** |

#### control_range字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| min | number | 是 | 最小值 |
| max | number | 是 | 最大值 |
| step | number | 是 | 步进值 |
| default | number | 是 | 默认值 |

### 1.4 执行器控制类型说明

| 控制类型 | 说明 | 适用设备 |
|----------|------|----------|
| boolean | 布尔值控制（on/off） | LED开关、继电器、水泵、蜂鸣器 |
| integer | 整数值控制（0-100） | 电机速度、亮度调节、风扇速度 |
| angle | 角度控制（0-180/360） | 舵机角度、阀门开度 |
| float | 浮点值控制 | 精确参数调节 |
| string | 字符串指令 | 自定义指令 |
| **rgb** | **RGB-LED专项控制** | **RGB灯带、彩灯** |

### 1.5 设备回馈数据（feedback字段）

执行器上报时可携带feedback字段，用于存储设备特有状态信息。不同执行器类型的feedback结构不同：

#### 通用feedback字段

| 字段 | 类型 | 说明 | 适用设备 |
|------|------|------|----------|
| state | string | 当前状态: on/off/error | 所有执行器 |
| control_value | number | 控制值 | 所有执行器 |
| direction | string | 旋转方向: forward/backward/stop | 电机、风扇 |
| speed | number | 当前速度 0.0-1.0 | 电机、风扇 |
| color | object | RGB颜色 {r,g,b} | RGB-LED |
| brightness | number | 亮度值 0-100 | RGB-LED、LED |
| pattern | string | 蜂鸣模式: alarm/success/warning/click | 蜂鸣器 |
| command_count | number | 命令计数 | 蜂鸣器 |
| pin | number | GPIO引脚号 | 蜂鸣器 |
| pins | object | GPIO引脚配置 | 所有执行器 |
| initialized | boolean | 初始化状态 | 所有执行器 |

**摄像头feedback字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| power | string | 电源状态：on/off |
| found | boolean | 是否检测到目标颜色 |
| resolution | string | 图像分辨率（如：640x480） |
| tracking_enabled | boolean | 是否启用颜色追踪 |
| is_running | boolean | 视频流服务是否运行 |
| color_preset | string | 当前颜色预设：blue/red/green/yellow/orange |
| available_colors | array | 支持的颜色列表 |
| pan_angle | number | 水平角度（0-180） |
| tilt_angle | number | 垂直角度（0-180） |
| stream_url | string | MJPEG 视频流地址（树莓派8081端口） |
| snapshot_url | string | 快照地址 |

- `alarm`: 连续长响

**Feedback保留机制**：
- 设备上报时如果**不包含**feedback字段，服务器会**保留原值**（使用COALESCE函数）
- 避免设备周期性上报时意外覆盖已存储的feedback数据
- 仅当设备**主动上报**feedback时才会更新

## 二、执行器控制协议

### 2.1 接口地址

```
POST /api/actuators/[id]/commands
```

### 2.2 控制命令格式要求

**⚠️ 重要提示**：
- 所有控制命令**必须包含 `control_type` 字段**
- 如果缺少 `control_type` 字段，命令将被默认识别为 `boolean` 类型
- RGB-LED控制命令**必须使用 `control_type: "rgb"`**

```json
  "command": "on"
}
```

### 2.4 请求格式（普通控制 - 数值）

```json

  "command": "value",
  "value": 75
}
```

## 三、硬件回执确认协议

### 3.1 双通道回执机制

硬件端应同时通过**WebSocket**和**HTTP**两种方式发送回执：

| 通道 | 延迟 | 说明 |
|------|------|------|
| WebSocket | <50ms | 主通道，实时性高 |
| HTTP PATCH | <15ms | 备份通道，确保可靠 |

**幂等处理说明**：
- 如果命令已是目标状态，直接返回成功
- 处理双通道回执的竞态条件
- 两个通道的回执到达顺序不确定，幂等处理确保不会出错

**摄像头 feedback 保留机制（v2.2.1 新增）**：
- PATCH 回执处理时，先检查数据库中已有 feedback 是否有数据（`hasExistingData` 检查）
- 若已有 feedback 包含数据（如 `stream_url`、`pan_angle` 等），则只更新回执携带的字段，**不覆盖**已有字段
- 若已有 feedback 为空，则跳过 feedback 写入，等待数据上报补充完整
- 此机制确保摄像头回执处理不会意外清空 `stream_url` 等关键字段

### 3.2 HTTP回执接口

```
PATCH /api/actuators/[id]/commands
```

### 3.3 HTTP请求格式（普通执行器）

```json
{
  "command_id": 8392,
  "status": "executed",
  "control_value": 75,
  "state": "on"
}
```

### 3.4 HTTP请求格式（RGB-LED）

```json
{
  "command_id": 8395,
  "status": "executed",
  "state": "on",
  "color": {"r": 255, "g": 128, "b": 0},
  "brightness": 60
}
```

### 3.5 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| command_id | number | 是 | 命令ID（从查询指令接口获取） |
| status | string | 是 | 执行状态（executed/failed） |
| control_value | number | 数值控制必填 | 实际执行的控制值 |
| state | string | 否 | 执行器状态（on/off） |
| color | object | RGB设备必填 | 颜色信息 {r, g, b} |
| brightness | number | RGB设备可选 | 亮度值 0-100 |

### 3.6 响应格式（首次回执）

```json
{
  "success": true,
  "message": "OK",

  "status": "executed"

```

## 四、查询待执行指令协议

### 4.1 接口地址

```
GET /api/actuators/[id]/commands
```

### 4.2 功能说明

硬件端轮询获取待执行的控制指令。服务器返回待执行指令后自动将状态标记为`executing`。

**注意**：硬件端查询时**不要**传递`frontend=true`参数，否则会进入前端快速查询模式。

### 4.3 查询模式区别

| 模式 | 参数 | 说明 | 响应时间 |
|------|------|------|----------|
| 硬件端 | 不传frontend | 执行超时清理，返回5条指令 | ~140ms |
| 前端 | ?frontend=true | 不清理超时，返回1条指令 | ~60ms |

### 4.4 路径参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | string | 是 | 执行器ID |

### 4.5 响应格式（有待执行指令 - 硬件端查询）

```json
{
  "success": true,
  "data": {
    "id": 8392,
    "actuator_id": "MT-1-1001",
    "command": "value",
```

## 五、区域划分规则

1. **网关级区域**：优先使用上报数据中的`area`字段
2. **IP默认区域**：如果没有提供`area`字段，使用`gateway_ip`生成默认区域名（如：区域-192.168.1.100）
3. **节点级覆盖**：单个设备可以通过`nodes[].area`字段覆盖网关级区域设置
4. **同一IP同一区域**：同一IP地址的设备默认属于同一区域

## 六、控制流程

### 6.1 完整控制流程

```
1. 用户点击控制按钮
      ↓
2. 前端发送 POST /api/actuators/{id}/commands
      ↓
3. 服务器创建指令（pending状态）+ 返回命令ID
      ↓
4. 服务器通过WebSocket推送指令到硬件
      ↓
5. 前端保存命令ID，开始300ms间隔轮询（?frontend=true）
      ↓
6. 硬件执行命令
      ↓
7. 硬件通过 WebSocket + HTTP 双通道发送回执
      ↓
8. 服务器更新指令为executed，更新执行器状态和feedback
      ↓
9. 前端轮询检测到**对应命令**的executed状态
      ↓
10. 【乐观更新】立即更新本地UI（~300ms延迟）
      ↓
11. 异步调用fetchActuators()同步服务器数据
```

### 6.2 命令ID跟踪机制

为避免多命令并发时状态混淆，前端实现命令ID跟踪：

1. **发送命令时保存命令ID**：服务器返回命令ID后，前端保存到 `pendingCommandIds` 状态
2. **轮询检查时验证命令ID**：前端轮询获取最新命令，检查命令ID是否与保存的ID匹配
3. **状态完成后清理命令ID**：命令执行成功/失败/超时后，清除对应的pendingCommandId

### 6.3 性能指标

| 阶段 | 延迟 | 说明 |
|------|------|------|
| 命令创建 | ~50ms | 服务器创建指令并存储 |
| WebSocket推送 | <50ms | 实时推送到硬件 |
| 硬件执行 | 视硬件而定 | 通常<100ms |
| WebSocket回执 | <50ms | 硬件发送回执 |
| HTTP回执 | <15ms | 双通道冗余 |
| 前端轮询检测 | ~60ms | 前端快速查询模式 |
| **乐观更新显示** | **~300ms** | 用户感知到的延迟 |

### 6.4 超时机制

- 控制指令发送后，服务器等待30秒回执
- 超时未收到回执，标记为`timeout`并提醒用户
- 超时后执行器自动解锁，允许重新发送指令
- 前端轮询超时时间：30秒

### 6.5 指令状态说明

| 状态 | 说明 |
|------|------|
| pending | 待执行（已创建，等待推送/执行） |
| executing | 执行中（已推送到硬件，等待回执） |
| executed | 已执行（收到硬件回执确认） |
| failed | 执行失败（硬件返回失败） |
| timeout | 超时（30秒未收到回执） |

### 7.2.1 Gateway 注册回退机制（v2.2.1 新增）

当硬件端通过 WebSocket 发送 `gateway_register` 消息时，如果消息中缺少 `gateway_ip` 字段，服务端会自动回退使用连接上下文 IP 地址，避免 SQL `undefined` 报错。

**硬件端注册消息格式**：
```json
{
  "type": "gateway_register",
  "data": {
    "gateway_id": "gw-001",
    "gateway_ip": "192.168.1.100",
    "gateway_type": "wifi_sensor",
    "farm_id": 1
  }
}
```

**注意**：`gateway_ip` 字段建议硬件端始终携带。若缺失，服务端将使用 WebSocket 连接的远程 IP 作为回退值。

### 7.5 心跳保活机制

1. **心跳间隔**: 每30秒发送一次心跳包
2. **超时检测**: 服务器超过60秒未收到心跳则断开连接
3. **重连策略**: 硬件端实现指数退避重连
   - 第1次重连: 等待1秒
   - 第2次重连: 等待2秒
   - 第3次重连: 等待4秒
   - 最大等待: 30秒

### 7.6 降级机制

当WebSocket连接断开时，系统自动切换到HTTP轮询模式：

1. **WebSocket在线**: 命令通过WebSocket实时推送（延迟<500ms）
2. **WebSocket断开**: 硬件端使用HTTP轮询获取待执行指令（默认每10秒）
3. **自动重连**: 硬件端实现指数退避重连策略，恢复WebSocket连接后自动切换回实时推送

## 十一、注意事项

1. **数据格式**：所有数值类型必须为数字，字符串必须用双引号
2. **时间格式**：使用北京时间格式（YYYY-MM-DD HH:MM:SS）
3. **编码格式**：请求体必须为UTF-8编码
4. **频率限制**：建议上报间隔不小于10秒
5. **重连机制**：网络中断后需实现自动重连
6. **错误处理**：收到非200响应时，建议采用指数退避策略重试
7. **双通道回执**：硬件端应同时通过WebSocket和HTTP发送回执
8. **Feedback保留**：设备上报时如果不包含feedback字段，服务器会保留原值
9. **命令ID跟踪**：前端需保存并验证命令ID，避免多命令状态混淆
10. **控制命令格式**：所有控制命令必须包含control_type字段，RGB控制必须使用control_type: "rgb"
11. **回执及时性**：硬件端应在执行完指令后立即通过双通道（WebSocket + HTTP）发送回执，确保前端UI及时更新

## 十二、控制更新及时性说明

### 延迟分析

控制指令从发送到前端UI更新的延迟主要由以下几个阶段组成：

| 阶段 | 延迟 | 说明 |
|------|------|------|
| 命令创建 | ~50ms | 服务器创建指令并存储到数据库 |
| 命令推送 | <50ms | WebSocket实时推送到硬件端（如果连接在线） |
| 硬件执行 | 视硬件而定 | 通常<100ms |
| 硬件回执 | <50ms | 硬件通过WebSocket或HTTP发送回执 |
| 服务器处理回执 | ~11ms | 服务器更新数据库状态，更新执行器feedback |
| 前端轮询检测 | ~60ms | 前端通过 `?frontend=true` 快速查询模式获取最新状态 |
| **乐观更新显示** | **~300ms** | 用户感知到的总延迟 |

### 硬件端优化建议

1. **立即回执**：硬件端执行完指令后应立即发送回执，不要等待其他操作完成
2. **双通道发送**：同时通过WebSocket和HTTP两种方式发送回执，确保至少一个通道能及时到达
3. **回执内容完整**：回执应包含完整的状态信息，包括RGB颜色、亮度等扩展数据
4. **避免阻塞**：回执发送不应阻塞主循环或任务调度
5. **摄像头线程同步（v2.2.1 新增）**：追踪线程和视频流线程共享 `picamera2` 实例时，必须使用 `threading.Lock()` 保护 `capture_array()` 调用，防止 V4L2 缓冲区竞争导致视频流中断
6. **追踪停止优雅化**：`stop_tracking()` 应通过锁同步等待追踪线程释放摄像头，而非 `join()` 阻塞命令处理线程（延迟从 3 秒降至 <100ms）

### 回执超时处理

- 服务器等待回执的超时时间为30秒
- 如果30秒内未收到回执：
  1. 指令状态标记为 `timeout`
  2. 执行器自动解锁（locked=0）
  3. 前端显示超时提醒
  4. 允许用户重新发送指令
- 硬件端应确保在30秒内完成执行并发送回执
