# 智慧农业物联网监控平台项目说明文档

## 更新日期：2026-07-31

---

## 1. 项目概述

智慧农业物联网监控平台是一个基于Next.js的现代化Web应用，用于实时监控和管理农业环境传感器数据与执行器设备。该平台提供了直观的仪表盘界面，展示温度、湿度、光照、土壤湿度等关键农业环境参数，支持设备自动发现、IP区域划分、多类型执行器控制、数据趋势分析和AI智能决策等功能。

### 主要功能

- **实时数据监控**：传感器数据实时采集与展示
- **设备自动分类**：硬件上报数据后自动识别传感器/执行器类别
- **IP区域划分**：基于IP地址自动划分设备区域，同一IP归为同一区域
- **多类型执行器控制**：支持布尔值、整数、角度、浮点、字符串、RGB六种控制类型
- **RGB-LED专项控制**：支持预设颜色、自定义RGB、白色亮度、颜色名称等多种控制方式
- **控制卡片自适应**：根据硬件上报的control_type自动加载对应控制UI（含RGB专项控制卡片）
- **回执确认机制**：发送指令后等待硬件回执，收到回执才更新页面
- **双通道回执**：WebSocket + HTTP双通道同时发送回执，支持幂等处理
- **乐观更新**：命令执行成功后立即更新前端UI，延迟从~2000ms降至~300ms
- **命令ID跟踪**：前端保存并验证命令ID，避免多命令并发时状态混淆
- **Feedback保留机制**：设备未上报feedback时保留原值，避免被意外覆盖
- **超时提醒**：30秒未收到回执自动标记超时并提醒用户
- **WebSocket实时通信**：指令实时推送，状态实时更新
- **数据趋势分析**：历史数据图表展示与对比分析
- **数据对比分析**：多传感器数据时间范围对比，支持12小时以上长时间范围查询
- **报警管理**：自定义报警规则与通知
- **AI智能决策**：基于LLM的智能诊断与自动控制
- **知识库管理**：农业知识库RAG检索增强
- **多农场/多区域管理**：支持多地点多项目管理
- **响应式设计**：适配不同设备屏幕

## 2. 技术栈

### 前端技术

- **框架**: Next.js 16.2.0 (App Router)
- **语言**: TypeScript
- **UI组件**: shadcn/ui
- **样式**: Tailwind CSS v4.2.0
- **图表库**: Recharts
- **图标库**: Lucide React
- **状态管理**: React useState/useEffect
- **实时通信**: WebSocket (原生)

### 后端技术

- **API框架**: Next.js API Routes
- **数据库**: MySQL / SQLite (双支持)
- **实时通信**: WebSocket (ws库)
- **AI服务**: OLLAMA + BAAI/bge-small-zh-v1.5
- **向量存储**: FAISS

### 硬件端

- **主控芯片**: STM32F103C8T6
- **WiFi模块**: ATK-MB026
- **通信协议**: HTTP + WebSocket
- **传感器**: 温度、湿度、光照、土壤湿度等15种
- **执行器**: 水泵、风扇、电机、舵机等11种

**指令状态说明**:
- `pending`: 待执行（已创建，等待推送/执行）
- `executing`: 执行中（已推送到硬件，等待回执）
- `executed`: 已执行（收到硬件回执确认）
- `failed`: 执行失败（硬件返回失败）
- `timeout`: 超时（30秒未收到回执）

**状态流转**:
```
pending → executing → executed
                    → failed
                    → timeout
```

## 5. 核心功能说明

### 5.1 设备自动发现与分类

硬件设备通过 `/api/device/report` 接口上报数据后，服务器自动完成：

1. **网关自动创建**：根据IP地址自动创建或关联网关
2. **设备类型识别**：根据 `type` 字段识别设备类别（传感器/执行器）
3. **ID自动生成**：统一生成格式 `{PREFIX}-{gatewayId}-{nodeId}`
4. **自动分类存储**：传感器数据存入sensors表，执行器数据存入actuators表
5. **类型自动注册**：新设备类型自动注册到对应类型表
6. **区域自动划分**：基于IP地址自动划分区域

### 5.2 IP区域划分机制

1. **同一IP同一区域**：同一IP地址上报的所有设备默认属于同一区域
2. **自定义区域名**：硬件上报时可通过 `area` 字段指定区域名称
3. **节点级覆盖**：单个设备可通过 `nodes[].area` 覆盖网关级区域设置
4. **区域视图**：`/areas` 页面按区域分组展示所有设备

### 5.3 执行器多类型控制

支持六种控制类型，硬件通过 `control_type` 字段指定：

| 控制类型 | 说明 | 适用设备 |
|---------|------|---------|
| boolean | 布尔值控制（on/off） | 水泵、LED灯、电磁阀、继电器、蜂鸣器 |
| integer | 整数值控制（0-100） | 电机速度、风扇档位、亮度调节 |
| angle | 角度控制（0-180/360） | 舵机、阀门开度 |
| float | 浮点值控制 | 精确参数调节 |
| string | 字符串指令 | 自定义指令、模式切换 |
| rgb | RGB-LED专项控制 | RGB灯带、彩灯，支持预设颜色/自定义RGB/白色亮度/颜色名称 |

**RGB-LED 6种控制方式**：

| 控制方式 | 方法 | 参数示例 |
|---------|------|---------|
| 开关控制 | command=value, value=0/100 | 关闭/全亮 |
| 预设颜色 | command=value, value=1-9 | 1=红, 2=绿, 3=蓝... |
| 白色亮度 | command=value, value=10-100 | 50=50%亮度 |
| 自定义RGB | command=color, r/g/b=0-255 | (255,128,0)=橙色 |
| 颜色名称 | command=preset, preset=颜色名 | red/green/blue等 |
| 浮点RGB | command=color, r/g/b=0-255 | 同自定义RGB |

**控制卡片自动加载逻辑**：
1. 优先使用硬件上报的 `control_type` 配置
2. 特殊识别RGB-LED：当 `type=light` 且 feedback 包含 R/G/B 字段或名称包含"RGB"时，自动加载RGB控制卡片
3. 默认布尔值控制：如果都没有配置，默认使用布尔值开关控制

### 5.4 回执确认与超时机制

**完整控制流程**：
1. 前端发送控制请求（所有控制命令必须包含 `control_type` 字段）
2. 服务器创建指令（pending），锁定执行器，返回命令ID
3. 前端保存命令ID到 `pendingCommandIds` 状态
4. 通过WebSocket推送指令到硬件端，同时通过HTTP转发接口（8081端口）备份推送
5. 前端显示"发送中"状态，每300ms轮询一次命令状态（使用 `?frontend=true` 快速查询模式）
6. 硬件执行指令
7. 硬件通过**双通道**发送回执（WebSocket + HTTP PATCH）
8. 服务器更新指令状态为executed，更新执行器状态和feedback数据，解锁
9. 服务器处理回执时支持**幂等操作**：如果命令已是目标状态，直接返回成功
10. 前端轮询检测到**对应命令ID**的executed状态后，**立即乐观更新**本地UI（无需等待服务器数据同步）
11. 前端异步调用 `fetchActuators()` 从服务器同步最新数据

**超时机制**：
- 超时时间：30秒
- 超时处理：指令标记为timeout，执行器自动解锁，前端显示超时提醒
- 支持重新发送指令

**性能优化指标**：

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 前端显示延迟 | ~2000ms | ~300ms | 6.7倍 |
| 状态轮询耗时 | ~1400ms | ~60ms | 23倍 |
| 数据库操作数 | 3次/请求 | 1次/请求 | 3倍 |

**双通道回执机制**：
- WebSocket通道：延迟<50ms，优先使用
- HTTP PATCH通道：延迟<15ms，备份通道
- 两个通道同时发送，确保回执可靠接收
- 支持幂等处理，重复回执不会报错

**命令ID跟踪机制**：
- 前端发送命令后保存服务器返回的命令ID
- 轮询检查时验证命令ID是否匹配，避免多命令并发时状态混淆
- 命令执行完成后清理保存的命令ID

**乐观更新机制**：
- 传统方式：发送指令 → 等待回执 → fetchActuators → 更新UI（~2000ms）
- 乐观更新：发送指令 → 轮询检测到executed → 立即更新本地UI → 异步同步（~300ms）
- 仅更新当前等待的命令状态，避免状态混淆

### 5.5 设备离线状态判断机制

**判断逻辑**：
- 设备在线状态不再仅依赖数据库中的 `status` 字段
- 在 API 查询层（`/api/sensors` 和 `/api/actuators`）基于 `last_update` 时间戳判断在线状态
- 设置 **5分钟** 为离线阈值，超过此时间未更新则判定为离线
- 计算公式：`(当前时间 - last_update时间) / 1000 / 60 <= 5`

**优势**：
- 实时反映设备实际状态，避免设备断电后仍显示在线的问题
- 无需依赖设备主动上报离线状态
- 前后端状态一致，UI显示准确

### 5.6 执行器类型自动注册与恢复机制

**支持的执行器类型**（共14种）：

| 类型标识 | 名称 | 控制类型 | 描述 |
|---------|------|---------|------|
| water_pump | 水泵 | boolean | 用于灌溉和排水控制 |
| fan | 风扇 | integer | 用于通风和温度调节，支持速度调节 |
| heater | 加热器 | integer | 用于温度控制 |
| valve | 电磁阀 | boolean | 用于水流控制 |
| light | 补光灯 | integer | 用于光照调节，支持亮度控制 |
| ventilator | 通风机 | boolean | 用于空气循环 |
| fogger | 雾化器 | boolean | 用于湿度调节和降温 |
| motor | 电机 | integer | 用于驱动控制，支持速度调节 |
| servo | 舵机 | angle | 用于角度控制，支持0-180度旋转 |
| led | LED灯 | boolean | 用于照明和指示，支持开关控制 |
| relay | 继电器 | boolean | 用于开关控制，支持通断操作 |
| laser | 激光器 | boolean | 用于激光控制，支持开关控制 |
| rgb_led | RGB-LED | rgb | 用于RGB颜色控制，支持6种控制方式 |
| buzzer | 蜂鸣器 | boolean | 用于声音提示，支持4种蜂鸣模式（alarm/success/warning/click） |

**自动注册流程**：
1. 数据库初始化时自动创建所有执行器类型（即使某些类型已被删除，也会自动检查并恢复）
2. 硬件上报设备数据时，系统自动查找对应类型
3. 如果类型不存在，自动从设备类型配置字典中创建
4. 自动检查每个必要的执行器类型，确保即使被删除也能恢复
5. 新设备类型（如激光设备、蜂鸣器）能正确识别和添加

**自动恢复机制**：
- 系统启动时逐个检查每个必要的执行器类型是否存在
- 如果类型不存在（被删除），自动从 `device-types.ts` 配置字典中重新创建
- 确保即使管理员误删了类型，硬件上报后仍能正确识别设备
- 详细的日志记录类型创建过程，便于排查问题

### 5.7 WebSocket实时通信

**连接地址**：`ws://localhost:8080`

**系统端口架构**：

| 进程 | 端口 | 职责 |
|------|------|------|
| Next.js开发服务器 | 3000 | HTTP API、前端页面渲染、数据库操作 |
| WebSocket服务器 | 8080 | WebSocket实时连接、命令推送、状态同步 |
| HTTP转发接口 | 8081 | HTTP命令转发到WebSocket连接（桥梁作用） |

**核心消息类型**：
- `command`: 服务器→硬件端，控制指令推送
- `command_ack`: 硬件端→服务器，命令回执（含RGB扩展格式）
- `command_status`: 服务器→前端，命令状态更新
- `area_sync`: 前端→服务器，订阅区域数据
- `area_update`: 服务器→前端，区域数据更新广播
- `heartbeat`: 双向，心跳检测（每30秒）
- `gateway_register`: 硬件端→服务器，网关注册

**降级机制**：
- WebSocket在线：命令通过WebSocket实时推送（延迟<50ms）
- WebSocket断开：自动切换到HTTP轮询模式，确保命令不丢失
- 硬件端实现指数退避重连策略：1秒→2秒→4秒→...→最大30秒

### 5.8 Feedback数据管理机制

**Feedback字段说明**：
- `feedback` 是JSON类型字段，存储在 `actuators` 表中
- 用于存储设备特有回馈数据，不同执行器类型结构不同
- 支持字段：state、control_value、direction、speed、color、brightness、pattern、command_count、pin、pins、initialized

**Feedback保留机制**：
- 设备上报时如果**不包含**feedback字段，服务器使用 `COALESCE(feedback, ?)` 保留原值
- 避免设备周期性上报时意外覆盖已存储的feedback数据
- 仅当设备**主动上报**feedback时才会更新
- 示例：风扇反馈（direction、speed）、蜂鸣器反馈（pattern、command_count、pin）、RGB-LED反馈（color、brightness）

### 5.9 数据对比分析功能

**功能说明**：
- 访问 `/compare` 页面进行多传感器数据对比分析
- 支持选择多个传感器和指定时间范围
- 支持12小时以上长时间范围查询
- 系统自动根据时间范围计算足够的数据点
- 支持数据重采样和统一时间轴，使用线性插值对齐不同传感器数据

**时间范围查询优化**：
- 计算公式：`limit = max(时间范围小时数 × 120 × 1.5, 300)`
- 确保长时间范围查询返回足够的数据点
- 支持按时间升序/降序排列

## 6. API接口文档

### 6.1 系统架构

平台采用分布式架构，由三个独立进程协同工作：

| 进程 | 端口 | 职责 |
|------|------|------|
| Next.js开发服务器 | 3000 | HTTP API、前端页面渲染、数据库操作 |
| WebSocket服务器 | 8080 | WebSocket实时连接、命令推送、状态同步 |
| HTTP转发接口 | 8081 | HTTP命令转发到WebSocket连接（桥梁作用） |

**命令下发流程**：
```
用户操作 → POST /api/actuators/{id}/commands → 写入数据库(pending)
    → HTTP POST http://localhost:8081/send-command → WebSocket推送命令
    → 硬件执行 → 双通道回执（WebSocket + HTTP）→ 更新数据库(executed)
    → 前端轮询检测 → 乐观更新UI → 异步同步
```

### 6.2 设备上报与控制API

#### POST /api/device/report
- **功能**: 硬件设备上报传感器和执行器数据（支持feedback字段）
- **详细说明**: 参见《硬件通信协议.md》

#### PATCH /api/actuators/[id]/commands
- **功能**: 硬件端确认控制指令执行结果（HTTP回执，支持幂等处理）
- **详细说明**: 参见《网页端控制硬件功能说明.md》

#### GET /api/device/ack
- **功能**: 硬件端查询待执行指令（HTTP轮询用）

### 6.3 传感器API

| 接口 | 方法 | 功能 |
|------|------|------|
| /api/sensors | GET | 获取传感器列表 |
| /api/sensors/[id] | GET | 获取单个传感器详情 |
| /api/sensors | POST | 新增传感器 |
| /api/sensors/[id] | DELETE | 删除传感器 |
| /api/sensors/[id]/data | GET | 获取传感器历史数据（支持时间范围查询） |
| /api/sensors/[id]/data | POST | 新增传感器数据 |

### 6.4 执行器API

| 接口 | 方法 | 功能 |

| /api/actuators/[id] | GET | 获取单个执行器详情 |
| /api/actuators | POST | 新增执行器 |
| /api/actuators/[id] | DELETE | 删除执行器 |
| /api/actuators/[id]/commands | POST | 发送控制指令（支持rgb控制类型） |
| /api/actuators/[id]/commands | GET | 查询命令历史/状态（支持?frontend=true快速查询） |
| /api/actuators/[id]/commands | PATCH | 硬件端回执确认（支持幂等处理） |

### 8.2 常见问题

**Q: API返回404错误？**
- 检查API路由文件是否在正确位置
- DELETE方法必须放在 `[id]/route.ts` 中

**Q: 数据不显示？**
- 检查数据库连接配置
- 确认传感器数据已正确上报
- 检查时间格式是否为北京时间（YYYY-MM-DD HH:MM:SS）

**Q: 执行器控制后状态不更新？**
- 检查硬件端是否通过双通道（WebSocket + HTTP）发送了回执
- 确认WebSocket连接是否正常
- 查看服务器日志和浏览器控制台
- 前端需检查是否收到对应命令ID的executed状态

**Q: 控制卡片显示不正确？**
- 检查执行器的control_type字段
- 确认硬件上报时是否包含control_type和control_range
- RGB-LED需检查feedback是否包含R/G/B字段，或名称是否包含"RGB"
- 刷新页面重新加载

**Q: RGB灯控制指令立即失败（400错误）？**
- 检查发送的命令格式是否正确：必须包含 `control_type: "rgb"` 字段
- RGB控制卡片已修复，直接构造包含control_type的完整请求体
- 硬刷新浏览器（Ctrl+Shift+R）清除缓存的旧JS代码

**Q: 控制页面更新不及时？**
- 检查WebSocket连接是否正常
- 确认硬件端通过双通道发送回执
- 前端轮询间隔应为300ms
- 如果WebSocket断开，检查HTTP转发接口（8081端口）是否正常运行

**Q: 设备类型被删除后不显示控制卡片？**
- 系统已实现自动恢复机制，启动时会自动重建被删除的类型
- 检查服务器日志中是否有类型创建的日志

**Q: Feedback数据被重置为null？**
- 设备上报时如果不包含feedback字段，服务器会保留原值（使用COALESCE函数）
- 确认设备是否在上报时正确发送了feedback字段

8. **双通道回执**：WebSocket + HTTP双通道同时发送回执，支持幂等处理
9. **乐观更新**：命令执行成功后立即更新前端UI，延迟从~2000ms降至~300ms
10. **命令ID跟踪**：精确验证命令ID，避免多命令并发时状态混淆
11. **Feedback保留机制**：设备未上报feedback时保留原值，避免被意外覆盖
12. **实时通信**：WebSocket实时推送，延迟<100ms
