## 一、项目概述

### 1.1 项目目标

构建一个生产级、可远程升级的物联网硬件网关，具备：

- **传感器自动发现**：扫描 I2C / GPIO / ADC / 1-Wire 接口，自动注册发现的设备
- **数据上传至云端**：默认上传所有扫描到的设备，支持白名单/黑名单过滤
- **配置热加载**：通过触摸屏修改配置后无需重启即可生效
- **OTA 远程升级**：支持 HTTP 拉取和 Git Pull 双模式，含备份和回滚
- **触摸屏 UI**：基于 Tkinter 的苹果风格简约界面，支持 1024×600 全屏
- **离线缓存重传**：网络异常时本地 SQLite 缓存，恢复后自动重传

### 1.2 核心特性

| 特性 | 描述 |
| --- | --- |
| 模块化架构 | 6 层分离：UI / App / Core / Services / Drivers / Scanner |
| 非阻塞状态机 | 所有耗时操作在子线程，主线程响应迅速 |
| 配置驱动 | 所有运行参数均可通过 `config/settings.yaml` 配置 |
| 自动降级 | Windows 开发时无 GPIO 自动进入测试模式 |
| 优雅停止 | 收到 SIGTERM/SIGINT 后安全停止所有线程 |
| 事件总线 | 模块间松耦合通信，支持订阅/发布 |

## 三、模块详细设计

### 3.1 配置管理 (`core/config_manager.py`)

**职责**：统一加载、读取、修改、热监控配置文件。

**特性**：
- 支持 `.` 分隔的嵌套键访问（如 `upload.server_url`）
- 5 秒间隔自动检测文件 mtime 变化，触发回调
- 修改后自动持久化到对应 YAML 文件
- 配置段映射：`sensors`→sensors.yaml、`actuators`→actuators.yaml、其余→settings.yaml

**关键配置项**：
- `upload.server_url`：上传服务器地址
- `upload.interval`：上传间隔（秒）
- `upload.upload_filter`：上传过滤模式（all/whitelist/blacklist）
- `ota.mode`：OTA 升级模式（http/git）
- `scanner.enabled_interfaces`：启用的扫描接口

### 3.2 系统主控 (`app/system.py`)

**职责**：协调所有模块的生命周期，处理信号。

**启动流程**：
1. 初始化 ConfigManager
2. 初始化 Logger
3. 初始化 CacheService / UploadService / HeartbeatService / OTAManager / DeviceScanner
4. 加载并初始化传感器和执行器
5. 启动配置热加载监控（5 秒间隔）
6. 启动心跳服务
7. 启动 OTA 自动检查
8. 启动数据采集线程（按 `upload.interval` 周期性采集并上传）
9. 启动缓存重传线程（每 60 秒检查本地缓存）
10. 启动 UI（如启用）

**优雅停止**：
- 收到 SIGINT/SIGTERM 设置 `_stop_event`
- 等待所有工作线程结束（5 秒超时）
- 清理所有 GPIO/I2C 资源
- 发布 `SYSTEM_STOP` 事件

### 3.3 上传服务 (`services/upload_service.py`)

**API 端点**：
- `POST /api/device/report`：批量上传传感器/执行器数据
- `GET /api/device/ack?gateway_ip=xxx`：拉取待执行指令
- `POST /api/device/ack`：发送指令执行回执

**数据格式**：
```json
{
  "gateway_ip": "192.168.1.63",
  "farm_id": 1,
  "area": "温室1号区域",
  "nodes": [
    {"node_id": "T-1-001", "type": "temperature", "name": "空气温度", "value": 25.6, "unit": "°C"}
  ]
}
```

**上传过滤**：
- `all`：上传所有设备（推荐，默认）
- `whitelist`：仅上传 `device_ids` 或 `device_types` 列表中的设备
- `blacklist`：排除 `device_ids` 或 `device_types` 列表中的设备

**失败处理**：
- 立即重试 `max_retries` 次，重试间隔按倍数递增
- 全部失败后写入本地 SQLite 缓存
- 缓存重传线程每 60 秒尝试上传

### 3.4 OTA 升级 (`ota/`)

**双模式架构**：
- **HTTP 模式**：从 `manifest_url` 获取版本信息，下载 tar.gz/zip 代码包，校验 checksum 后解压安装
- **Git 模式**：通过 `git fetch` + `git reset --hard origin/main` 更新代码

**升级流程**：
1. `check_update`：检查是否有新版本
2. `backup_current`：备份当前代码到 `.backup/backup_YYYYMMDD_HHMMSS/`
3. `download`：下载新版本（仅 HTTP 模式）
4. `install`：解压并覆盖项目文件（排除 .git/logs/data 等目录）
5. `verify`：验证关键文件存在且可导入核心模块
6. 失败时自动 `rollback`：从最新备份恢复

**自动升级**：
- `auto_check_enabled`：每小时检查一次
- `auto_update`：发现新版本后自动升级（默认关闭，仅通知）

### 3.5 设备扫描 (`scanner/`)

**支持的接口**：
| 接口 | 检测方法 | 设备类型示例 |
| --- | --- | --- |
| I2C | 扫描 0x03-0x77 地址，查询已知设备表 | BMP280(0x76), MPU6050(0x68), LCD1602(0x27) |
| GPIO | 对每个引脚尝试 `Button(pin)`，读取电平 | 振动/倾斜/按键/PIR |
| ADC | 读取 MCP3008 通道，超过阈值的判定为有设备 | 光照/土壤湿度/声音 |
| 1-Wire | 扫描 `/sys/bus/w1/devices/` 目录 | DS18B20 温度传感器 |

**扫描结果**：
- 转换为 `sensors.yaml` 格式并保存
- 重复扫描不会覆盖已有配置（按 ID 去重）

### 3.6 触摸屏 UI (`ui/`)

**设计原则**：苹果风格简约设计，符合 7 寸触摸屏操作习惯。

**界面结构**：
```
┌────────────────────────────────────┐
│ 状态栏：时间 | 标题 | 退出按钮      │  ← 顶部
├────────────────────────────────────┤
│                                    │
│         当前页面内容                │  ← 中间
│                                    │
├────────────────────────────────────┤
│ 仪表盘 | 网络 | 设备 | 扫描 | 升级  │  ← 底部 Tab
└────────────────────────────────────┘
```

**5 个页面**：
1. **仪表盘**：系统运行状态、设备数量、服务器信息、上传统计
2. **网络配置**：服务器地址、上传间隔、心跳设置（可保存并热加载）
3. **设备管理**：已配置设备列表、上传过滤模式设置
4. **设备扫描**：选择接口、执行扫描、查看结果、保存到配置
5. **在线升级**：检查更新、执行升级、查看进度、回滚

### 4.5 服务端回执修复（2026-08-07）

**问题**：颜色追踪开关（track）和手势控制开关（gyro）命令执行后，WebSocket 服务器和 `/api/device/ack` 路由对所有命令都强制覆盖执行器 `state`，导致 `track off` / `gyro off` 等子命令把摄像头状态错误设为 `off`，前端误显示摄像头已关闭。同时 WebSocket 数据上报路径未更新 `feedback` 字段，导致 `tracking_enabled`、`gesture_control_enabled` 等运行时状态无法通过 WebSocket 同步到数据库。

**修复内容**：
- [x] `websocket-server.js` `handleCommandAck`：为 track/gyro/color/reset 命令添加 `shouldUpdateState` 检查，仅解锁不改变 state；传递 `state` 参数优先使用硬件回传值
- [x] `websocket-server.js` `handleDataReport`：为执行器节点更新 `feedback` 字段，确保运行时状态同步
- [x] `app/api/device/ack/route.ts`：同步添加 `shouldUpdateState` 检查，不覆盖 feedback 字段

**影响**：颜色追踪开关和手势控制开关的 state 不再被回执错误重置，前端可正确显示追踪状态和手势控制状态。

**处理内容**：

- [x] `app/areas/page.tsx`：`fetchActuators()` 仅对改变 state 的命令调用，且延迟 2 秒避免竞态

### 4.11 MJPEG 视频流中断修复（2026-08-10）

**问题**：关闭手势控制/颜色追踪后，视频流会消失几秒后才恢复。虽然 4.9/4.10 已修复 `state` 不被错误覆盖、`fetchActuators()` 不被不必要调用，但视频流仍短暂中断。

**根因分析**：

MJPEG 流使用 HTTP 长连接（`multipart/x-mixed-replace`），浏览器通过持续接收分块数据来显示视频。React 重渲染时，即使 `<img>` 的 `src` 属性值不变，React 的 reconciliation 过程仍会触碰 DOM 属性，导致浏览器重置 MJPEG 连接。

当 `setActuators` 更新 `actuator` 对象时（如 `gesture_control_enabled` 变化），`CameraControlCard` 组件重新渲染：
1. React 对比新旧 Virtual DOM，发现 `src` 值相同
2. 但仍会更新 DOM 属性（React 不会跳过已存在的属性）
3. 浏览器检测到 `src` 属性被重新设置，中断旧 MJPEG 连接并重新发起请求
4. 重新建立连接需要几秒，期间视频流消失

**修复方案**：使用 `ref` + `useEffect` 通过 DOM API 直接管理 `src`，完全绕过 React 的 JSX 属性绑定：

- [x] `camera-card.tsx`：新增 `imgRef` 引用 `img` 元素
- [x] `camera-card.tsx`：`useEffect` 仅在 `streamUrl` 实际变化时通过 DOM API 设置 `src`
- [x] `camera-card.tsx`：`img` 标签移除 `src` 属性（JSX 中不设置），添加 `ref={imgRef}`
- [x] `camera-card.tsx`：`key={streamUrl}` 确保仅在 URL 变化时重新挂载元素
- [x] `camera-card.tsx`：`handleReloadStream` 改用 `ref` + `requestAnimationFrame` 实现手动重载
- [x] `camera-card.tsx`：`onLoad`/`onError` 改用 `useCallback` 稳定回调，避免每次渲染创建新函数

**关键逻辑**：
```tsx
// img 标签不设置 src，由 useEffect 通过 DOM API 直接管理
const imgRef = useRef<HTMLImageElement>(null)

useEffect(() => {
  if (imgRef.current && streamUrl) {
    imgRef.current.src = streamUrl  // 绕过 React reconciliation
    setStreamLoading(true)
    setStreamError(false)
  }
}, [streamUrl])

// JSX 中不设置 src
<img ref={imgRef} key={streamUrl} onLoad={handleStreamLoad} onError={handleStreamError} />
```

**效果**：
- 切换手势控制/颜色追踪时，`streamUrl` 不变 → `useEffect` 不执行 → `img.src` 不被触碰 → MJPEG 连接保持
- 仅在 `streamUrl` 实际变化时（如摄像头重启），`useEffect` 才更新 `src` 建立新连接
- `key={streamUrl}` 确保 URL 变化时 React 重新挂载元素，避免旧连接残留

### 4.12 硬件端视频流中断修复（2026-08-10）

**问题**：4.11 前端修复后，关闭颜色追踪时视频流仍短暂消失。经排查确认问题出在硬件端。

**根因分析**：

`camera_tracker.py` 的 `stop_tracking()` 方法使用 `_async_raise`（`PyThreadState_SetAsyncExc`）强制终止追踪线程。当追踪线程正在 `picam2.capture_array()` 中（C 扩展调用，持有 V4L2 缓冲区）时被强制杀死，会导致：

1. V4L2 缓冲区未正确归还到队列，进入不一致状态
2. 后续 `capture_array()` 调用（视频流服务）超时或失败
3. 视频流暂时中断，直到 V4L2 驱动自行恢复

此外，追踪循环中 OpenCV 处理占用大量 CPU，长时间持有 GIL，导致视频流线程调用 `capture_array()` 时被阻塞。

**处理内容**：

- [x] `camera_tracker.py` `stop_tracking()`：移除 `_async_raise` 强制杀线程，改用标志位 + `join(timeout=3.0)` 优雅关闭
- [x] `camera_tracker.py`：移除 `_async_raise` 方法及 `ctypes`/`inspect` 导入
- [x] `camera_tracker.py` `_tracking_loop`：`capture_frame()` 返回 None 时检查 `_is_running` 立即退出
- [x] `camera_tracker.py` `_tracking_loop`：捕获帧后立即检查 `_is_running` 退出标志
- [x] `camera_tracker.py` `_tracking_loop`：每帧处理后 `time.sleep(0)` 主动让出 GIL
- [x] `camera_tracker.py` `capture_frame()`：增加 50ms 重试机制，提高 V4L2 缓冲区恢复后的帧获取成功率

**关键逻辑**：
```python
# 修改前：强制杀线程，可能损坏 V4L2 缓冲区
def stop_tracking(self):
    self._is_running = False
    self._async_raise(self._track_thread.ident, SystemExit)  # 危险！
    self._track_thread.join(timeout=1)

# 修改后：优雅关闭，线程自然退出
def stop_tracking(self):
    self._is_running = False
    self._track_thread.join(timeout=3.0)  # 等待线程自然退出
```

**影响**：
- 关闭颜色追踪时，追踪线程在 3 秒内自然退出，不再强制杀线程
- `picam2.capture_array()` 正常完成，V4L2 缓冲区状态保持正确
- 视频流服务持续获取帧，流不中断
- `time.sleep(0)` 让出 GIL 确保视频流线程不被饿死

### 4.13 摄像头线程同步修复（2026-08-10）

**问题**：4.12 修复后，关闭颜色追踪/手势控制时视频流仍短暂中断，需等待数秒才恢复。

**根因分析**：

`camera_tracker.py` 中 `capture_frame()` 定义了 `self._lock = threading.Lock()`（第58行）但从未使用。两个线程共享同一个 `picamera2` 实例且无同步保护：

| 线程 | 调用链 |
|---|---|
| 追踪线程 | `_tracking_loop` → `capture_frame()` → `picam2.capture_array()` |
| 视频流线程 | `_handle_stream` → `get_jpeg_frame()` → `capture_frame()` → `picam2.capture_array()` |

摄像头 "on" 命令（`system.py` 第1482行）会自动调用 `start_tracking()`，追踪线程始终在后台运行。当切换追踪/手势时，两个线程同时争抢 V4L2 缓冲区，导致视频流卡顿。

**处理内容**：

- [x] `camera_tracker.py` `capture_frame()`：`picam2.capture_array()` 调用前加 `with self._lock` 保护，确保同一时间只有一个线程访问摄像头
- [x] `camera_tracker.py` `stop_tracking()`：设置 `_is_running = False` 后，通过 `with self._lock: pass` 等待追踪线程释放锁，确保当前帧捕获完成后才返回
- [x] `websocket-server.js` `handleGatewayRegister()`：修复 gateway_ip 为 undefined 时的 SQL 参数错误，回退到连接上下文中的 IP

**关键逻辑**：
```python
# 修改前：无锁保护，两个线程同时调用 capture_array()
def capture_frame(self):
    if self._picamera:
        return self._picamera.capture_array()  # 竞争！

# 修改后：加锁保护，线程安全
def capture_frame(self):
    if self._picamera:
        with self._lock:                               # 锁保护
            return self._picamera.capture_array()      # 安全

# 修改前：非阻塞退出，追踪线程可能仍在 capture_array() 中
def stop_tracking(self):
    self._is_running = False

# 修改后：等待追踪线程释放锁，确保无竞争
def stop_tracking(self):
    self._is_running = False
    with self._lock:
        pass  # 等待追踪线程完成当前 capture_array()
```

**影响**：
- 关闭颜色追踪/手势控制时，视频流不再中断
- 锁同步仅等待当前 `capture_array()` 调用完成（通常 <100ms），延迟极低
- 追踪线程与视频流线程互斥访问摄像头，V4L2 缓冲区状态一致

## 六、技术支持

- **硬件平台**：树莓派 5 + 7 寸触摸屏
- **操作系统**：Raspberry Pi OS (Linux ARM64)
- **Python 版本**：3.11+
- **配置文件**：YAML（UTF-8 编码）
- **依赖管理**：pip + requirements.txt

如需新增传感器/执行器，遵循以下步骤：
1. 在 `drivers/sensors/` 或 `drivers/actuators/` 创建驱动文件
2. 继承 `BaseSensor` 或 `BaseActuator`
3. 实现 `initialize()` / `read()` 或 `execute_command()` / `cleanup()`
4. 在 `app/system.py` 的 `_get_sensor_driver_map` 注册
5. 在 `config/sensors.yaml` 或 `config/actuators.yaml` 添加配置项
